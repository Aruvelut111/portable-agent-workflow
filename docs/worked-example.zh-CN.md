# 完整案例：为本地资料浏览器增加搜索

[中文正文](../README.md) · [English](worked-example.en.md)

本例用一个假设需求说明，库、方案选择、任务分工和交付检查如何连接起来。应用、任务和结果均为说明性设定，本仓库不提供该应用的实现。

## 1. 区分使用目标与候选方案

假设已有一个本地资料浏览器，支持目录浏览和打开文件。用户提出：“资料太多，增加搜索功能；是否可以用向量数据库，再安排几个 Agent 一起做？”

这里可以确定的目标是提高资料查找效率。向量数据库与多 Agent 是候选方案，还需要结合现有应用判断。

现场调查发现：主要资料为文本与 Markdown，常见查询是术语、文件名和原句；已有读取模块可以复用；部分附件尚不能解析；原文件应保持只读，内容留在本机。基于这些条件，当前可先实现全文检索，并让结果返回原文位置。语义检索保留为后续选项，待真实查询暴露词面检索的不足后再比较。

这项选择需要记录原因，而不仅是“采用全文搜索”。如果以后用户开始大量按概念提问，或者资料类型发生变化，接手者就能判断原选择是否仍适用。

## 2. 从库中找到可用部分

项目记录提供当前版本、运行入口和已有决定；工具登记用于定位读取器、检索组件和页面控制能力；知识库提供已确认的格式、编码与定位问题；相关 Skill 只在需要其方法时读取。

查到候选组件后，用几份代表资料核对读取、查询和返回格式。关键问题是：已有读取器能否保留原文位置，检索结果能否被页面使用，文件变化后旧位置如何失效。登记未命中时，再查项目代码、相近用途和公开实现；不能将一次搜索结果当作能力全貌。

这里的复用范围可以很小：保留现有读取器，引入成熟全文检索组件，新增必要的结果适配。只有这些部分无法满足目标时，才考虑更大范围替换。

## 3. 先明确接口，再决定是否并行

若检索与结果面板已有清楚边界，可以分别安排成员；若修改量很小，由一个 Agent 完成更直接。需要并行时，先确认两边对结果的理解一致：

| 接口内容 | 要解决的问题 |
|---|---|
| 稳定的文档标识与可打开位置 | 排序、刷新或重建索引后，结果仍能指向正确文档 |
| 命中位置及位置的表示方式 | 检索返回的位置能被页面正确解释，避免字符偏移与字节偏移混用 |
| 索引所依据的文件版本 | 文件变化后能够识别旧片段和旧位置 |
| 片段与展示信息 | 页面能显示可理解的结果，不必重新猜测原文含义 |
| 本次处理范围与失败情况 | 无匹配、部分输入未处理和执行失败能够区分 |

这些是双方需要共同理解的内容，具体字段可以沿用现有应用。接口不必为了通用性重新设计一套协议。

成员分别修改所属模块，各用独立的开发索引。主应用与主索引由集成负责人更新；接口需要变化时先协调相关依赖，再把决定写回项目。

一个可直接开工的任务描述可以是：

> 为现有资料浏览器接入全文检索。输入为用户选定目录中的文本和 Markdown，原文件只读，数据留在本机。复用现有读取模块，检索组件可根据适用性选择。你负责检索模块及相应检查，页面模块由另一成员负责；位置、版本和覆盖信息需与页面接口一致。交付实际修改、运行命令和代表输入的结果，注明读取失败或尚不支持的部分。产物放在本次约定的项目目录；共享接口变化需与集成负责人协调。

真实派发时应填入输入、代码和交付的具体位置。委派者可以附候选组件，但不应将候选写成不可调整的实现要求。

## 4. 用实际使用检查接口含义

索引返回结果后，将它接入面板，检查从查询到打开原文的过程。代表性检查可以包括：

- 查询一份包含中文与英文的资料，点击命中片段，确认文件和定位均正确。
- 修改命中段落后刷新，确认索引与定位已更新，或旧版本被明确识别。
- 保留一个不能读取的附件，确认检索范围与失败信息可见。

这些检查各自针对一个可能改变结果的风险。第一项检查位置表示，第二项检查更新与失效，第三项检查空结果的解释范围。

如果页面打开了正确文件却定位错误，就沿读取、索引、接口和页面比较位置值及其含义，找到最早出现的差异。单独重跑索引或调整 UI，都不能替代这次定位。

“没有结果”也需要限定范围：当前可读文本里没有匹配，与全部资料中不存在相关内容，是不同结论。用户和 Agent 应能继续查看附件、原件和诊断信息。

## 5. 中断后依据当前产物继续

接力记录可以包含：

> 当前目标：在本地检索资料，并从结果返回原文。文本与 Markdown 的全文检索已接入结果面板，修改、运行方式和检查结果见本次交付。采用全文检索的依据是现有查询以术语和原句为主。附件解析与自动更新尚未完成。下一步从现有刷新入口检查文件修改后的重新索引。开发索引相互独立，主索引由集成负责人维护。

真实记录中，需要链接实际产物、检查使用的输入版本和当前工作区。接手者先确认文件状态，继续未完成的工作。若先前更新可能已经提交，就先查看其结果，再决定是否重复执行。

## 6. 完成后的维护位置

实现、测试和实验留在项目中；可独立复用的检索组件补入工具登记；新确认的格式或位置语义进入知识库；经反复使用确有价值的方法再整理为 Skill。项目记录更新当前产物、未完成范围和下一步，过程输出按本次授权范围处理。

本例首先解决查询与原文定位。附件、自动更新和语义查询仍是后续能力，不能因为首条路径已经跑通就被视为完成。是否增加 MCP 或持续调度，应由外部调用与任务派发的真实需求决定。
