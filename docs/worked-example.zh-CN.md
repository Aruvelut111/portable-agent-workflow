# 完整例子：给本地资料浏览器增加搜索

[返回正文](../README.md) · [English](worked-example.en.md)

这是一个假设案例，用来展示工作关系。文件、任务和结论均为示意；这里没有实现或测试这个应用。

## 从需求推导一个能实施的方向

用户说：“资料越来越多，想让 AI 帮我搜。我听说向量数据库很好，你们多开几个 Agent 搞一下。”

负责人先看当前应用和资料特点。假设现场已有目录浏览器，主要资料是文本和 Markdown，用户经常按术语、文件名和短语寻找原文；还存在暂不能读取的附件。用户希望资料保留在本机。

由此形成当前推荐：先复用现有文件读取逻辑与成熟的全文检索能力，在浏览器里增加关键词搜索、原文定位和覆盖说明。语义检索是否值得接入，留待真实查询暴露缺口后再比较。用户的例子启发了调查，没有把某一种数据库变成默认目标。

这条首路径要走到“用户输入一个词，看到命中位置，并能打开正确原文”。同时保留尚未覆盖的需要：附件读取、增量更新、重复资料和语义查询。首路径不代表整个需求已经完成。

## 从库里拿什么

负责人按当前问题查找已有入口：

- 能力登记：现有读取器、搜索接口与界面测试的实际调用方式及限制。
- 知识库：资料格式、编码和索引覆盖相关的已确认事实。
- 可复用流程：只有当前需要的导入或交付方法。
- 项目台账：现有应用的当前版本、已做决定、实际运行入口和相关工作。

如果登记没有命中，继续查看项目代码或公开库。一次未命中只说明该入口没找到。发现一个现成组件后，核对它是否真正能处理选定输入，以及它的输出能否接到当前界面。

## 怎样安排协作

假设此时有两项可以独立推进：一位成员调查并接入索引接口，另一位成员实现结果面板。负责人先明确共用的搜索结果语义，再让两边在不重叠的文件范围里工作。

结果至少需要让消费者知道：原文件身份、命中位置、片段和本次搜索覆盖范围。完整字段随应用需要决定。成员可以直接讨论位置表示，影响公共接口的决定再同步给负责人。

工作副本各自使用独立索引文件，集成时由负责人更新主应用。这样既隔离代码，也避免两个进程同时改同一份运行数据。若任务很小，负责人直接完成同样合理。

## 一份可动手的任务说明

> 在当前资料浏览器中接入已有全文检索能力，让所选文本和 Markdown 能返回命中片段及原文位置。以当前工程入口和用户选定目录为输入，原始资料只读。修改范围为检索模块及其现有测试；需要改变公共结果接口时与集成负责人协调。交付可调用实现、实际修改和复跑方式。完成判断：代表输入可检索、位置能被结果面板使用、不能读取的输入有明确覆盖说明。可替换候选组件，理由留在当前记录里。

说明给了目标和边界，具体检索方案由执行者判断。没有要求把所有调查结果都复制到任务卡里。

## 走到实际消费者

索引成员说“接口能返回结果”以后，负责人仍需把它接到实际面板。一个可区分问题的检查，是点开某条命中后，原文是否定位到了正确位置。这个检查同时覆盖结果身份与界面消费。

再选一项有意义的变化：修改一份示例资料并刷新，观察新内容是否进入搜索、旧位置是否更新。若位置错误，沿文件读取、索引位置编码、接口运输和面板解释寻找第一处分歧。不要先用界面偏移量补偿来源错误。

如果附件未被读取，界面应准确说明当前搜索覆盖了哪些输入。负责人继续保留附件能力的待办；一次空结果不能被转述为“资料里没有这个内容”。

## 中断时保存什么

一条简短接力记录可以是：

> 目标：资料在本机可检索并回到原文。当前实现与运行入口见本次交付；关键词路径已接入结果面板。决定：先用全文检索，待真实查询显示语义缺口再比较扩展。已确认的检查及输入版本见对应记录。仍待解决：附件覆盖与增量更新。下一步：沿现有刷新入口接入一次文件变更，用同一份资料核对旧位置更新。两个开发副本的索引互相独立，主索引由集成者更新。

实际记录需要指向真实产物和检查结果，不能只保留上面的示意文字。接手者先检查当前实现；如果上次的写入已提交，就从未完成动作继续。

## 结束后留下什么

实现与相应测试留在项目。若产生可跨项目复用的检索组件，就更新能力登记。已证实的新格式事实进入知识库；只有反复有用的接入方法才进入 Skill。项目台账保存当前结论与下一步。一次性索引和过程输出按本次范围清理。

完成本例不要求建设统一平台、发布 MCP，或把所有内容写成固定模板。新增结构应能解释它减少了哪项重复或错误。
