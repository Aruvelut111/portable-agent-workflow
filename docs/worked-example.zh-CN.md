# 举个例子：给本地资料浏览器加搜索

[返回正文](../README.md) · [English](worked-example.en.md)

用一个假设例子，看看这套做法怎么用。下面的应用和结果都是为了说明过程，这个仓库里没有实现它。

## 一句需求，先想想怎么做

假设我已经有一个资料浏览器，能打开本地文件夹。资料越来越多，我跟 Agent 说：“帮我加个搜索吧，要不搞个向量数据库，多开几个 Agent 一起做。”

我想要的是找资料方便一点。Agent 看过以后发现，大部分是文本和 Markdown，我平时经常按术语、文件名、原句查找，也有一些还读不了的附件。资料需要留在本机。

那就可以先复用现有读取功能，加上全文搜索，让结果能点回原文。以后碰到关键词解决不了的查询，再研究语义检索。这时保留附件、自动更新、重复资料等后续需求，先把一次搜索从头到尾接起来。

## 先翻一下已有的东西

Agent 可以先看工具登记，找现成的读取器、搜索接口和页面操作方法。资料编码和格式的问题，去知识库里查。相关 Skill 用到再读。项目台账能告诉它现在的版本、入口和之前的决定。

如果登记里没找到，继续看代码或公开库。找到候选以后，拿几份资料试一下，看看返回的结果能不能接到现在的页面。顺便保留打不开的输入和原始报错，后面排查会用到。

## 要分工，先把两边接得上的地方说清楚

假设索引和结果面板可以分开做。一个 Agent 负责读取、索引和查询，另一个做页面。

它们得先说清搜索结果怎么表示：是哪份文件、命中在什么位置、显示哪段文字，以及这次实际搜索了哪些资料。具体字段按应用来定。位置的格式需要讨论，就直接讨论，改动决定记回项目。

代码可以各自改不同文件，开发时各用一份索引。最后负责接起来的 Agent 更新主应用，避免两边同时写同一份运行数据。如果整件事很小，一个 Agent 做完也行。

给索引这边的任务，可以这样说：

> 给当前资料浏览器接上全文搜索。先处理用户选定目录里的文本和 Markdown，原文件只读，复用现有读取和搜索功能。搜索结果要有片段和原文位置，让页面能点回去。你负责检索模块和相关测试，需要调整共用接口时，跟页面这边商量。交付修改、运行方法，以及几份代表资料的结果；读不了的输入也说明一下。候选组件不合适可以换，留下原因。

够它开工就行，没必要把所有检索经历塞进去。

## 接到页面，才看得出中间缺没缺东西

索引能返回结果以后，还得接到面板。挑一个词搜，点开一条结果，看看是不是正确文件、正确位置。这一步能发现接口两边对位置的理解有没有差别。

然后改一份示例资料，刷新，再查一次。新内容有没有进来，原来的位置有没有更新？如果错行，就从文件读取、索引位置、接口传递到页面定位逐步看，找到最早出问题的地方。

附件还读不了，就在结果里说明这次覆盖了哪些资料。暂时没搜到的内容仍然可以再查，不能就此认定所有资料里都没有。

## 中间停了，留下什么

一条接力记录可以很短：

> 目标是本地搜索，并能回到原文。关键词结果已接到页面，修改和运行方法见本次交付。先用全文搜索，语义检索等真实查询有需要再比较。还差附件和自动更新。下一步沿现有刷新入口，检查一次文件修改后的重新索引。开发副本各用自己的索引，主索引由集成这边更新。已做检查及输入版本见记录。

真实项目里要把这些说明换成实际文件和链接。下一位先看现在的文件，再继续没做完的部分，免得重复写入或重跑。

## 收尾以后，东西放回哪里

实现和测试留在项目里。如果做出了以后还能用的搜索组件，就补工具登记。确认了新的格式或编码特点，写进知识库。某个方法反复好用，再整理成 Skill。台账留下当前结论和下一步，一次性索引、过程输出按本次范围清理。

这件事做完，再看哪里还费劲。真正需要持续派活，或者接入别的程序时，再决定要不要加编排工具或 MCP。
